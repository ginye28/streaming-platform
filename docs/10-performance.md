# 렌더링 성능 — 낮은 사양 기기에서도 부드럽게

시안의 유리 질감(`backdrop-filter`), 번지는 빛(큰 `blur`·그림자), 끝없이 도는 움직임은 그래픽 자원을 많이 쓴다.
구형 폰·태블릿에서도 끊기지 않게 **기기를 보고 효과를 줄이는** 장치를 넣었다. 내용·배치·색은 그대로 두고 효과만 걷어 낸다.

## 무엇을 했나

| 구분 | 내용 |
|---|---|
| 등급 | `<html data-perf="full\|lite">`. `lite` 는 불러오는 자리의 반짝임·썸네일 확대·호버 전환·들어올 때 떠오르는 움직임·LIVE 점 깜빡임·빈 화면 그림의 둥둥 움직임을 끈다 (`web/src/perf.js`, `home.css`·`cinema.css`·`shell.css` 의 `data-perf='lite'` 규칙) |
| 자동 판정 | ① 브라우저 힌트: 데이터 절약, 메모리 ≤ 2GB, 코어 ≤ 2 → 처음부터 `lite` ② 처음 화면이 가라앉은 뒤 약 90프레임을 재서 **중앙값이 34ms 넘으면(약 30fps 미만)** `lite` 로 내림, 7일간 기억 |
| 사용자 선택 | 로그인 후 내 메뉴 → **화면 효과**: 자동 → 가볍게 → 전체. 선택은 자동 판정보다 우선. 로그아웃 상태는 주소에 `?perf=lite` / `?perf=full` / `?perf=auto` |
| 안내 | 자동으로 줄였을 때 한 번 알려 주고 "되돌리기"를 둔다(숨기지 않는다) |
| 모든 기기 공통 | 카드마다 반복되던 작은 알약(LIVE 배지·시청자·하트·음파)의 blur 를 짙은 배경으로 대체 · 카드의 홀로그램 회전(conic-gradient)은 올려 볼 때만 · `/assets` 장기 캐시 · stomp 는 필요할 때만 로드 |
| 움직임 줄이기 | OS 의 "동작 줄이기"를 켠 사람은 기존대로 모든 움직임이 꺼진다 |

캔버스 입자(빛 알갱이)는 현재 구현에 없다. 앞으로 넣는다면 `usePerf().level === 'lite'` 일 때 그리지 않고, `document.hidden` 일 때 멈추고, 입자 수를 `devicePixelRatio`·화면 크기로 제한한다.

## 기기에서 직접 재 보기

주소 뒤에 `?fps=1` 을 붙이면 왼쪽 아래에 계기판이 뜬다(그 기기에 기억됨, `?fps=0` 으로 끔).

```
58 fps · 최악 24ms
full (auto) · 8코어 · 8GB · dpr 3
```

- `fps` 는 지난 1초 평균, `최악` 은 그 1초 중 가장 긴 프레임이다. 최악이 50ms 를 넘으면 사람 눈에 끊겨 보인다.
- 마지막 줄의 `full`/`lite` 와 괄호(`auto`/`lite`/`full`)로 어떤 등급이 적용됐는지 본다.
- 같은 화면을 `?perf=full` 과 `?perf=lite` 로 번갈아 열어 차이를 비교한다.

### 확인 체크리스트

| 기기 | 화면 | 확인 | 결과(fps / 최악ms) |
|---|---|---|---|
| 최근 폰 | 홈 · 가로 스크롤 | 60fps 근처, `full` | |
| 구형 폰(2~3GB) | 홈 · 가로 스크롤 | `lite` 로 자동 전환되고 부드러운지 | |
| 구형 폰 | 라이브 시청(영상+채팅) | 채팅이 쌓여도 끊기지 않는지 | |
| 태블릿 | 홈 · 구독 상품(3D 카드) | 카드 기울기 애니메이션 | |
| 데스크톱 | 홈 · 카드 위에 마우스 | 호버 진행 상태가 펼쳐지는지 | |

> **이 표는 비어 있다.** 이 저장소를 만든 환경에서는 실제 구형 기기로 돌려 볼 수 없었다. 자동 전환 로직과 `lite` CSS 는 데스크톱 브라우저에서만 확인했다.
> 기기에서 돌려 본 뒤 숫자를 채우고, `SLOW_FRAME_MS`(`perf.js`) 기준이 너무 민감하거나 둔하면 조정한다.

## 알려진 한계

- 프레임 측정은 처음 한 번이다. 시청 화면(영상 디코딩 + 채팅)처럼 나중에 무거워지는 화면의 끊김은 잡지 못한다. 그런 기기는 메뉴에서 직접 `가볍게` 를 고른다.
- 자동 판정이 틀려 멀쩡한 기기가 `lite` 가 될 수 있다(처음 화면이 잠깐 무거울 때). 그래서 안내와 "되돌리기"를 두었다.
- 영상 자체의 부하(1080p 디코딩)는 이 장치로 줄지 않는다. 낮은 화질 선택은 아직 없다.

## 라이브 시청이 끊기거나 늦을 때 (수업 13명 제보 이후)

**측정한 것** (로컬 Docker, Chrome 152 MediaRecorder H.264 → `/ingest` → ffmpeg 복사 → HLS)
- 조각 길이는 움직이는 화면·정지 화면 모두 **약 3.37초**였다. ffmpeg 의 `-hls_time` 이 아니라 Chrome 이 키프레임을 내는 간격(약 100프레임)이 정한다. 복사 모드라 키프레임에서만 자를 수 있고, 서버(무료 0.1 CPU)가 다시 인코딩할 수는 없다.
- 시청 지연은 조각 3개를 따라가는 hls.js 기본값이면 이론상 약 10초 + 조각이 닫히기까지 3초대, 이번에 2개로 줄여 **재생기 기준 지연 5~6초**로 재졌다(`?fps=1` 계기판의 "지연").
- 이미 있던 한계: 무료 서버의 자바가 영상 조각을 직접 내려 주므로 시청자가 10명을 넘으면 CPU·대역폭이 먼저 닿는다(`docs/06-deployment.md` "수업·여럿이 볼 때").

**바꾼 것**
| 구분 | 내용 |
|---|---|
| 지연 | 재생기가 방송 끝에서 조각 2개 뒤를 따라간다 · 조금 뒤처지면 1.15배속으로 따라잡고 · 5개 넘게 뒤처지면 끝으로 건너뛴다 · 12초 넘게 뒤처지면 "지금 방송으로" 버튼 |
| 끊김 | 조각·재생목록 읽기 재시도 6번 · 지난 영상 30초만 보관 · 채팅·시청자 수 연결이 끊기면 2초부터 두 배씩(최대 30초) 늘려 다시 연결 |
| 부하 | 브라우저 방송은 1.5Mbps · 최대 1280×720 (이전 2.5Mbps · 1080p). 13명 기준 서버·와이파이를 지나가는 양이 최대 33 → 20Mbps |
| 한도 | 한 반이 같은 IP 로 나가는 경우를 기준으로 조회 1500 · 변경 300 · 연결 300 (분당, IP 별) |
| OBS | 키프레임 2초 · 1500kbps · 720p 로 맞추도록 안내하고, nginx 조각을 2초로 줄임 |

**시청 화면 `?fps=1`** 에는 이제 재생 상태도 나온다: 지연, 버퍼, 대역폭 추정, 화질, 끊김 횟수, 버린 프레임.
수업 중 끊긴다는 제보가 오면 이 값을 먼저 본다. 지연이 계속 커지면 서버가 못 따라가는 것이고, 버퍼가 0 근처이고 대역폭이 방송 비트레이트보다 낮으면 시청자의 망 문제다.

**아직 못 한 것**
- 운영(Render 무료) 서버의 실제 영상 전송 속도는 재 보지 못했다(운영에 재현할 방송이 없었다). 위 지연 수치는 로컬 기준이다.
- 실제 `getDisplayMedia`(화면 공유)의 키프레임 간격은 확인하지 못했다. 정지 화면에서 프레임이 드물게 나오면 조각이 더 길어질 수 있다 — 캔버스를 거쳐 일정한 프레임을 만드는 방법이 있지만, 방송 탭이 백그라운드가 되면 타이머가 느려지는 위험이 있어 넣지 않았다.
- 근본 해결(조각을 API 가 아닌 곳에서 내려 주기)은 계정·키가 필요해 하지 않았다.

## 지연 2초 이내 — 저지연 중계 (WebSocket + MSE)

HLS 로는 5~6초가 바닥이다(조각이 3.4초이고 조각이 닫혀야 받는다). 수업(디스코드 대체)에는 2초 안팎이 필요해서
브라우저 방송에 한해 **조각 없이 바로 흘리는 경로**를 더했다. HLS 는 그대로 남아 대체 경로가 된다.

```
선생님 브라우저 --0.25초 조각(WebM/H.264)--> /ingest --> ffmpeg ─┬─ HLS 조각 (대체 경로)
                                                              └─ 0.1초 fMP4 --> LiveRelay --WebSocket /watch--> 시청자 MSE
```

- MSE 는 WebM 안의 H.264 를 받지 않는다(실제 브라우저에서 확인: `isTypeSupported` false). 그래서 서버 ffmpeg 가 영상은 복사하고 소리만 AAC 로 바꿔 짧은 fMP4 로 다시 포장한다.
- 시청자는 방송 끝에서 약 0.8초 뒤를 따라가며, 조금 뒤처지면 1.04~1.1배속으로 따라잡고 3초 넘게 뒤처지면 끝으로 건너뛴다.
- 늦게 들어온 시청자는 머리(init)와 마지막 키프레임부터의 조각을 받는다(서버 메모리, 최대 6MB).
- 서버·브라우저가 못 하면 자동으로 HLS: 지원 안 하는 브라우저, 코덱 오류, 연결 실패(3번 재시도), 느린 시청자(큐 10초 초과), 저지연 상한 초과.

### 측정 (Docker 로 Render 무료와 같은 한도: 0.1 CPU · 512MB · 자바 힙 300MB, 맥 한 대에서 시청자를 흉내 냄)

| 조건 | 결과 |
|---|---|
| 방송만, 시청자 0 | CPU 약 2% (소리 인코딩을 1번으로 줄이기 전 약 4%) |
| **저지연 13명**, 1.5Mbps | 서버 CPU 4.3% · 모두 1.6Mbps 수신 · 조각 간격 p95 203ms · **최대 공백 0.57초** · 탈락 0 |
| 저지연 30명 | CPU 3.8% · 최대 공백 0.64초 · 탈락 0 · 메모리 470MB |
| 저지연 50명 | CPU 4.6% · 최대 공백 1.0초 · 탈락 0 · **메모리 508/512MB(한계)** → 상한 30 |
| HLS 13명 / 30명 | CPU 4.5% / 6.7% · 조각 받는 시간 최대 1.3초(조각 길이 3.3초 이내) |
| **실제 브라우저 시청자** (0.1 CPU, 다른 시청자 12명 동시) | 85초 동안 **끊김 0 · 버린 프레임 0**, 재생기 지연 1.4~1.6초, 영상 시계 기준 **종단 지연 1.6~1.7초** |

부하 시험이 잡아낸 결함 3가지(모두 고침):
1. 느린 시청자를 끊는 순간 구독자 목록을 순회 중에 수정해 `ConcurrentModificationException` → 중계 스레드가 죽어 방송 전체가 멈췄다(회귀 테스트 추가).
2. 코어가 1개로 보이는 컨테이너에서 가상 스레드로 전송하니 한 시청자의 블로킹 전송이 전원을 20~40초 굶겼다 → 시청자마다 일반 스레드.
3. **WebSocket 메시지 압축(permessage-deflate)** 이 이미 압축된 영상을 또 압축해 CPU 를 다 썼다. 13명에서 총 전송량이 약 11Mbps 에서 막혔고, 압축을 끄자(`WebSocketNoCompressionFilter`) 같은 서버에서 21Mbps 를 CPU 4%로 보냈다.

### 알아 둘 것 (측정하지 못했거나 남은 한계)
- **운영 Render 에서는 재지 못했다.** 위 수치는 로컬 Docker 의 한도 흉내다. Render 의 실제 CPU 배분·네트워크·Cloudflare 경유 지연은 다를 수 있다. 배포 후 시청 화면 `?fps=1` 의 "저지연 · 지연 N초"로 확인한다.
- 지연 약 1.6~1.8초는 **버퍼 약 0.8~1.5초를 둔 값**이다. 학교 와이파이가 흔들리면 멈추지 않도록 이 버퍼가 먼저 소모된다. 더 줄이려면 `lowLatency.js` 의 `TARGET_SECONDS` 를 낮추되 멈춤이 늘 수 있다.
- OBS 방송은 이 경로가 없다(HLS, 지연 약 5~8초). OBS 에서 RTMP 를 받아 같은 중계로 보내는 것은 아직 하지 않았다.
- 소리는 수업용으로 **모노 24kHz 48kbps** 다(CPU 절약). 음악 방송에는 맞지 않는다.
- 실제 `getDisplayMedia` 화면 공유의 키프레임 간격은 확인하지 못했다. 저지연 경로는 키프레임이 드물어도(처음 들어올 때만 영향) 지연에는 영향이 없지만, 중간 합류 시 첫 화면이 늦을 수 있다.
- 한 서버(메모리)만 가정한다. 서버를 여러 대로 늘리면 중계 허브를 바깥 저장소로 옮겨야 한다.
- 정말 큰 규모(수십~수백 명)는 WebRTC 미디어 서버(UDP 가능한 VM)가 맞다.
