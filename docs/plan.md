# 계획 설계서 (plan.md)

## 0. 주제 변경 사유 (v1)

처음에는 "클라이밍 완등 기록 웹앱"을 계획했으나, 2026-07-29부터 개인적으로 만들어 온
**라이브 스트리밍 플랫폼(SP)** 이 이미 배포·운영 단계까지 와 있어서 이쪽으로 주제를 바꿨다.
처음부터 새로 만들기보다, 실제 서비스 수준으로 완성도를 끌어올리는 쪽이 남는 시간에 더 의미 있다고 판단했다.

## 1. 한 줄 소개

방송(RTMP 송출)을 HLS로 실시간 시청하고, 채팅·구독·후원까지 되는 유튜브형 라이브 중심 스트리밍 플랫폼.

## 2. 누구를 위한 것인가

- **스트리머**: 방송 키로 OBS 등에서 송출하고, 채팅 운영·구독/후원 수익·방송 예약을 한 곳에서 관리하고 싶은 개인 방송인
- **시청자**: 좋아하는 채널을 구독하고, 라이브 채팅에 참여하고, 놓친 방송은 다시보기로 보고 싶은 사람

## 3. 핵심 기능 3가지

1. **라이브 방송·시청**: RTMP 수신 → HLS 변환(nginx-rtmp), 시청자 수, 방송 예약·대기실, 종료 후 다시보기(채팅 리플레이 동기화)
2. **실시간 채팅과 운영**: WebSocket(STOMP) 채팅, 매니저·금칙어·채팅 제한·슬로우 모드·공지 고정
3. **수익화**: 토스페이먼츠 유료 구독(등급), 후원(슈퍼챗), 환불, 정산 내역, 멤버십 전용 방송

## 4. 완성의 기준 (측정 가능)

- [x] 백엔드 자동 테스트 269개 통과, 실제 MySQL 대상 스키마 검증 테스트 통과

- [ ] 운영 환경(Render + TiDB)에서 토스 테스트 결제 승인 → 결제 내역 반영 확인

## 7. 알려진 한계 · 다음 계획

- 무료 서버(Render)는 15분 무접속 시 잠들어 첫 요청이 느리다.
- 운영 환경에는 RTMP 수신 서버가 없어 **실제 송출은 로컬에서만** 시연된다. (무료 VM 또는 터널로 확장 예정)
- 슬로우 모드·시청자 수·채팅 브로커가 서버 메모리 기반이라 서버를 여러 대로 늘리려면 Redis 등이 필요하다.
- 내부 RTMP 콜백에 공유 비밀값 검증이 아직 없다.

## 8. 중간 점검 일정 (제안)

- 1차: 운영 환경 결제 승인 재확인 + 문서·README 현행화
- 2차: 운영 RTMP 노출(터널) 또는 시연 영상 확보, 한계 항목 중 1개 해결
- 최종: 시연 영상 + 문서 + 회고
